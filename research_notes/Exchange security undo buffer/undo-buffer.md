# AI gateway undo buffer for Solana USDC

Research date: 7 November 2026. Scope is Prune as a proposed buffer for an AI-proposed family USDC transfer, the Solana point of no return, real pre-send buffers, and Circle freeze. Facts below are limited to pages fetched or search extracts cited inline. Product conclusions are under Inferences, not mixed into Cited Findings.

## Does Prune sit in front of model calls only, or can it hold, delay, or reverse a blockchain transaction?

### Takeaway
Prune's own docs describe a managed proxy in front of LLM providers. Shield spend caps run before the model provider is called. Those pages do not describe holding, delaying, or reversing a blockchain transaction.

### Cited Findings
- Prune's docs index calls Prune "a managed AI gateway": change the SDK base URL, add a Prune API key, and responses include a cost/security receipt. The quick start says spend caps are checked before the provider is called, and the sample client points `base_url` at `https://api.withprune.com/v1` for an OpenAI chat completion. — [Prune documentation](https://www.withprune.com/docs)
- "How it works" calls Prune "a managed AI proxy." The documented lifecycle is: app → Prune proxy → Shield → cache lookup → optimize → provider → response plus `prune_metadata`. Shield runs rate limits, spend caps, and allowlists "before any upstream call." Rejected requests "never reach the model." Upstream providers named on that page are OpenAI, Anthropic, Gemini, Bedrock, Ollama, OpenRouter, "or one of 6 more direct providers." — [How Prune works](https://www.withprune.com/docs/how-it-works)
- Shield controls listed there are per-key rate limits, daily spend caps (atomic Redis counters), model and IP allowlists, canary-token injection for system-prompt leakage, and reversible PII tokenization before upstream calls. Rejections return `X-Prune-Shield-Code` (examples: `spend_cap`, `rate_limit`). — [How Prune works](https://www.withprune.com/docs/how-it-works)
- The security model says Shield spend caps and rate limits "run before every upstream call and fail closed." If policy or today's spend cannot be loaded, the request returns HTTP 503 with `X-Prune-Shield-Code: shield_unavailable` and "does not bypass caps and call the provider." Daily spend uses atomic Redis `INCRBYFLOAT` so concurrent requests cannot overshoot a cap between read and write. Caps are checked "before the upstream LLM call fires." — [Prune security model](https://www.withprune.com/docs/security)
- The same security page distinguishes fail-closed money controls from fail-open cache: if the response cache is down, the call is treated as a cache miss and sent to the provider. Provider keys in the vault use AES-256-GCM; Prune API keys are stored as HMAC-SHA256 hashes. — [Prune security model](https://www.withprune.com/docs/security)
- A signed receipt is an Ed25519 signature over LLM `prune_metadata` (cost, cache, optimizations). The verify page says to fetch `https://api.withprune.com/v1/public-key` and check `receipt_signature`. It describes LLM cost receipts, not Solana transactions. — [Verify a signed LLM cost receipt](https://www.withprune.com/verify)
- The Prune homepage describes the product as sitting between an app and OpenAI, Anthropic Claude, Google Gemini, and OpenRouter, with semantic cache, model routing, and provider API keys kept in Prune. — [Prune homepage](https://www.withprune.com/)
- A site search for blockchain, wallet, Solana, and transaction on `withprune.com` returned the homepage, the how-it-works page, the security model, the security policy, and the receipt-verify page. The search synthesis was that those results do not describe Solana wallets or transactions. — [site search](https://www.withprune.com/)

### Inferences
- Prune can refuse or cap the model call that would draft a transfer message. That is a control on LLM spend and prompts, checked before OpenAI, Anthropic, or a similar provider.
- Nothing in the cited Prune pages puts Prune on the path that signs or submits a Solana transaction. Using Prune as the buffer that "unsends" a family USDC transfer is a product idea, not a behavior those docs describe.
- A button, queue, or timer inside the app, after the model has already replied, is an application control. It is not a security boundary unless some other system withholds the signing key or the tokens sit in a program that refuses to move them. Prune's fail-closed behavior applies to the LLM request, not to a later chain broadcast.

### Gaps
- These notes do not cover every Prune URL, the dashboard, or unpublished features. The finding is that the docs index, how-it-works, security model, homepage, and a site search for chain terms do not describe a blockchain hold, delay, or reversal.
- No Prune page fetched here states a formal "we never touch wallets" guarantee. Absence from those pages is not the same as an audited negative claim.

## On Solana, what is the point of no return for a USDC transfer?

### Takeaway
A USDC transfer is not a Solana transaction until it is signed and submitted. `sendTransaction` accepting it is not confirmation. Under Alpenglow, live on mainnet since 21 October 2026, `confirmed` and `finalized` both mean the transaction is permanently committed and cannot be rolled back. `processed` can still change. Some RPC and payments pages still describe the older Tower BFT split, where `confirmed` was reversible in principle and `finalized` took about 12.8 seconds.

### Cited Findings
- A transaction includes one or more instructions, the signatures of accounts that authorize the changes, and a recent blockhash. All instructions run together. If any instruction fails, the whole transaction fails and all state changes are reverted. "One signature is required for every signer account referenced by the transaction's instructions." Each signature is a 64-byte Ed25519 signature of the serialized message. The first signature is the fee payer's and is the transaction id. — [Transactions](https://solana.com/docs/core/transactions); [Transaction structure](https://solana.com/docs/core/transactions/transaction-structure)
- The recent blockhash is a timestamp and a deduplication key. "A blockhash expires after 150 slots." If it is no longer valid when the transaction arrives, the transaction is rejected with `BlockhashNotFound`, unless it is a valid durable-nonce transaction. — [Transaction structure](https://solana.com/docs/core/transactions/transaction-structure)
- The Solana cookbook still explains expiry as about 60 to 90 seconds, because it assumes slots of about 400ms to 600ms and a max processing age of 150 (151 recent blockhashes in the queue). It also says the default is that transactions expire if not committed in that window. — [Confirmation and expiration](https://solana.com/developers/cookbook/transactions/confirmation)
- Slot time was reduced separately from Alpenglow, from 400ms to 200ms, in four stages that completed in October 2026. — [Alpenglow](https://solana.com/upgrades/alpenglow)
- Durable nonce transactions replace the recent blockhash with a stored nonce and remove the 150-slot expiry window, so a signed transaction can be submitted later. The nonce authority can advance the nonce. Solana's payments docs say each nonce value can be used once, and advancing the nonce "mak[es] any transaction signed with the old value permanently invalid." The durable-nonce page says durable nonces may be deprecated in a future release. — [Durable nonces](https://solana.com/docs/core/transactions/durable-nonces); [Deferred execution](https://solana.com/docs/payments/advanced-payments/deferred-execution)
- `sendTransaction` "submits a signed transaction to the cluster and returns its first signature if the RPC accepts it." It "does not alter the transaction in any way." A successful response "does not guarantee the transaction is processed or confirmed by the cluster." The node retries until the transaction is finalized or the blockhash expires. Preflight verifies signatures and simulates the transaction. Clients are told to use `getSignatureStatuses` to see processed and confirmed status. — [sendTransaction](https://solana.com/docs/rpc/http/sendtransaction)
- Current RPC commitment text, still written in Tower BFT terms: `processed` is the newest view and "can still change if the cluster switches forks"; `confirmed` is a supermajority (two-thirds) vote and "still a weaker guarantee than `finalized`"; `finalized` is maximum vote lockout recognized by at least two-thirds of stake and "the strongest commitment level." — [sendTransaction](https://solana.com/docs/rpc/http/sendtransaction); [getTransaction](https://solana.com/docs/rpc/http/gettransaction)
- `getSignatureStatuses` reports `confirmationStatus` as `processed`, `confirmed`, or `finalized`. `confirmations: null` means the transaction is rooted and finalized by a supermajority of stake. — [getSignatureStatuses](https://solana.com/docs/rpc/http/getsignaturestatuses)
- Alpenglow, Solana Foundation, page updated October 2026: "Alpenglow is live on mainnet. It activated in epoch 1064, which started on Wednesday, October 21, 2026, at approximately 13:36 UTC." Votor shipped in Agave 4.3 and has been live since that epoch. Rotor is not yet scheduled. "Execution is untouched: the SVM, transactions, programs, and fees stay the same." Finality targets roughly 150 milliseconds, described as an expectation measured against the stake distribution at test time, not a constant. Under Tower BFT, finality was about 12.8 seconds. — [Alpenglow](https://solana.com/upgrades/alpenglow)
- The same Foundation page: "`confirmed` and `finalized` now describe the same state." "`processed` is unchanged and still means only that the transaction executed in a bank." New code should listen for `finalized`. "`confirmed` will be deprecated and removed in a later release." There is "no new status between `processed` and `finalized`." — [Alpenglow](https://solana.com/upgrades/alpenglow)
- Anza's commitment page, Alpenglow section: "`Confirmed` and `Finalized` commitment statuses are equivalent: both mean that a transaction has been permanently committed to the ledger and cannot be rolled back." The table marks "Target tx is committed to the permanent ledger" for confirmed and finalized, and not for processed. The vote condition listed is "60%+ stake voted finalize or 80%+ stake voted notarize on block." The Tower BFT table on the same page still shows finalized as requiring 31 or more confirmed blocks on top, which is the pre-Alpenglow rule. — [Solana commitment status (Agave)](https://docs.anza.xyz/consensus/commitments)
- Conflict, still published after the upgrade page: Solana payments verification says act on `finalized` for anything irreversible, and that a `confirmed` transaction "has a supermajority vote but can, rarely, still be dropped." A separate verification-tools page says a `processed` transaction can be dropped during forks, and suggests waiting for `confirmed` (1–2 seconds) or `finalized` (~13 seconds) for high-value transactions. — [Verifying a payment](https://platform.solana.com/docs/payments/accept-verification); [Verification tools](https://solana.com/docs/payments/accept-payments/verification-tools)
- Circle's USDC terms, section "On-chain transactions irreversible": "When USDC is sent to a third-party USDC address, such transaction is completed on USDC Supported Blockchains. This means that such transaction is irreversible and Circle does not have the ability to reverse or recall any transaction once initiated." The sender "bear[s] all responsibility for any losses" from sending to an incorrect address. Circle also says it has no ability or obligation to prevent or mitigate attacks or other issues on a USDC supported blockchain. Solana is listed as a supported chain; the mainnet mint published by Circle is `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v`. — [USDC terms](https://www.circle.com/legal/usdc-terms); [USDC contract addresses](https://developers.circle.com/stablecoins/usdc-contract-addresses)

### Inferences
- Before the required signatures exist, there is no transaction for the cluster to execute. Dropping an unsigned message has no ledger effect.
- After a recent-blockhash transaction is signed, anyone who has the signed bytes can submit it until the blockhash expires. The signer does not get a documented "unsign" call. Not broadcasting it is only safe if nobody else has the bytes and the blockhash ages out.
- A signed durable-nonce transaction does not age out on that 150-slot clock. The documented cancellation is to advance the nonce before anyone lands the old signed transaction. That invalidation is itself a transaction the nonce authority must sign and submit.
- `sendTransaction` returning a signature is not the point of no return. The node will keep retrying, and the transaction can still fail to land if the blockhash expires first.
- As of 7 November 2026, the point of no return described by the Solana Foundation and by Anza is `confirmed` / `finalized` under Alpenglow: permanent ledger commitment, aimed at roughly 150ms after the block is proposed, not a guaranteed constant. `processed` is earlier and is not that commitment.
- A finalized USDC transfer is not reversible by an AI gateway, by the sender, or by Circle recalling the payment. Circle's own terms say Circle cannot reverse or recall a transaction once it has been sent to a third-party address. Circle's phrase is "once initiated," which these terms do not map onto Solana's `processed` / `confirmed` / `finalized` labels.
- The cookbook's 60–90 second expiry and the payments pages' ~13 second finality describe the pre-200ms-slot, pre-Alpenglow timing. They should not be cited as the current wait after 21 October 2026 without noting that conflict.

### Gaps
- This research did not recompute wall-clock blockhash expiry after the October 2026 move to 200ms slots. Official structure docs still say 150 slots. They do not restate that window in seconds. The 60–90 second figure is tied to the cookbook's 400–600ms assumption.
- No fetched Solana RPC page documents a method to retract a transaction after `sendTransaction` has relayed it.
- This research did not fetch the SPL Token `Transfer` instruction page, so the notes do not quote that page's signer list. The general rule that every referenced signer must sign is cited above.
- RPC reference pages and the payments verification page still describe `confirmed` as weaker than `finalized`. The October 2026 upgrade page and Anza's Alpenglow table say they are now the same irreversible state. Both are published Solana sources. The upgrade page and Anza are the ones that explicitly discuss post-Alpenglow meaning.

## What real pre-send buffers exist, and what must be enforced on-chain?

### Takeaway
A buffer that can still return the USDC is one that has not yet produced a finalized transfer to the recipient. Documented versions are: do not sign; do not broadcast a recent-blockhash transaction and let it expire; advance a durable nonce to kill a signed-but-unsent payload; a Squads-style vault that will not execute until threshold, optional timelock, and a separate execute step; or a program escrow whose refund path still works because the counterparty has not completed the trade. A hold that exists only in the app UI is not a security boundary. The tokens have to be controlled by a key or program the app cannot move alone.

### Cited Findings
- Signature rule and relay rule: every signer account referenced by the instructions must have a signature, and `sendTransaction` relays the client-built transaction as-is after verifying signatures. It does not create the authorization itself. — [Transaction structure](https://solana.com/docs/core/transactions/transaction-structure); [sendTransaction](https://solana.com/docs/rpc/http/sendtransaction)
- Durable-nonce invalidation: advancing the nonce makes any transaction signed with the previous nonce value permanently invalid. That is a documented way to cancel a signed transaction that has not yet been consumed. — [Deferred execution](https://solana.com/docs/payments/advanced-payments/deferred-execution)
- Squads v4 multisig account stores `threshold` and `time_lock`. The docs define `time_lock` as "How many seconds must pass between transaction voting settlement and execution." A config change bumps `stale_transaction_index`, and "all transactions up until this index are stale." If `config_authority` is the default pubkey, config changes go through member voting; any other config authority must sign config changes ("controlled multisig"). — [Squads v4 accounts](https://docs.squads.so/main/development/reference/accounts)
- A Squads proposal "allow[s] it to be executed once the multisig threshold has been met." The proposal account stores keys that approved, rejected, and cancelled. The cancelled list is documented as "Keys that have cancelled (Approved only)." The vault transaction account stores the message to execute; it is not itself the completed transfer. — [Squads v4 accounts](https://docs.squads.so/main/development/reference/accounts)
- Squads' approve-proposal page: "Proposals require approvals equal to the threshold for the underlying transaction to be executed." A member needs Voter permission. Approval fails if the proposal is stale (`transactionIndex` < `staleTransactionIndex`). — [Approve proposal](https://docs.squads.so/main/development/typescript/instructions/approve-proposal)
- The Squads TypeScript overview lists separate program actions: create vault transaction, create proposal, approve, reject proposal, cancel proposal, and execute transaction. The quickstart runs those as separate confirmed transactions: create the vault transaction and proposal, then vote, then `vaultTransactionExecute`. The example transfer's source is the vault PDA, not the member's personal account. — [Squads TypeScript overview](https://docs.squads.so/main/development/typescript/overview); [Squads quickstart](https://docs.squads.so/main/development/introduction/quickstart)
- Permissions can split members into proposers, voters, and executors, so the key that creates a proposal need not be a key that can execute it. — [Squads permissions](https://docs.squads.so/main/development/reference/permissions)
- Chainstack's escrow-pattern doc describes a program, not a base-layer Solana feature. The maker deposits token A into a vault. The taker completes the swap in one transaction, or the maker calls `refund` and the program returns token A from the vault to the maker and closes the escrow. Both `take` and `refund` close the vault. The doc says only the maker signs `refund`. It also says Solana transactions are atomic, so a failed `take` rolls back the vault release. — [Solana: the escrow pattern (Chainstack)](https://docs.chainstack.com/docs/solana-escrow-pattern)
- Blueshift's Anchor escrow lesson describes the same three-instruction shape: `make` deposits, `take` completes, `refund` returns the vaulted tokens to the maker and closes the accounts. It states that after `refund` executes, "the offer is void." — [Anchor escrow refund (Blueshift)](https://learn.blueshift.gg/en/challenges/anchor-escrow/refund)

### Inferences
- The human signature is a real buffer only when the app and the model never hold the key and never receive a signature they can submit. That constraint is enforced by Solana's signature checks, not by a disabled button. If the backend holds the key, a UI delay can be skipped by any code path with that key.
- A Squads vault buffers the payment only while the USDC actually sits in the vault and the execute instruction has not been confirmed. Threshold, voter-only keys, and `time_lock` are fields the program stores. Reject and cancel are program instructions. After `vaultTransactionExecute` reaches the Alpenglow confirmed/finalized state, the inner transfer is a normal Solana transaction and follows the point of no return above.
- An escrow buffers a payment only when the tokens have already moved into a program vault whose code still allows the sender to refund, and the recipient's completion instruction has not landed. A direct transfer into a family member's token account is not this pattern. A screen that says "escrow" or "unsent" while the tokens remain in a wallet the app can sign for is a UI state, not a security boundary.
- These buffers have to be set up before the spend. They do not reach backward into a transfer that already finalized to the recipient's account.
- Chainstack and Blueshift document a widely taught program pattern. They are not a single shared Solana escrow protocol that automatically wraps USDC transfers.

### Gaps
- Squads spending-limit instructions are named in the TypeScript overview (`Add Spending Limit`, `Remove Spending Limit`). This research did not fetch the spending-limit rules, so it does not describe what a spending limit blocks.
- This research did not fetch Squads' reject, cancel, or execute instruction pages beyond the overview, quickstart, approve page, and account structs. The account struct shows cancel keys exist and labels them "Approved only." It does not, in the fetched text, spell out whether cancel is refused after execution.
- No official Solana core doc fetched here defines a protocol-level "unclaimed transfer" or sender timelock for an ordinary SPL transfer. The timelock cited is Squads' `time_lock` on a multisig. The escrow cited is a program pattern from Chainstack and a Blueshift course, not the Solana runtime.
- Durable-nonce deprecation is flagged by Solana as possible ("may be deprecated"). No fetched page gives a removal date.

## Can Circle freeze USDC, and is that the same as the sender unsending a normal transfer?

### Takeaway
Circle's terms and access-denial policy say Circle can block addresses and freeze USDC in defined legal, sanctions, and security cases. Circle also says a transfer to a third-party address is irreversible and that Circle cannot reverse or recall it once initiated. A freeze keeps a balance in place and stops it moving. It is not the sender taking a completed payment back. USDC in a Circle Mint account is not deposit-insured, and these notes do not treat USDC as an insured deposit.

### Cited Findings
- USDC terms: Circle "reserves the right to 'block' certain USDC addresses and, if such addresses are Circle custodied addresses, freeze associated USDC (temporarily or permanently)" that Circle determines may be associated with illegal activity or a terms violation. If a user sends USDC to a blocked address or receives USDC from one, Circle may freeze that USDC and terminate the USDC account. The user "may forfeit any rights associated with your USDC, including the ability to redeem USDC for USD." Circle may also freeze USDC and/or surrender USD held in segregated accounts if a valid government authority orders it. — [USDC terms](https://www.circle.com/legal/usdc-terms)
- The same terms: "USDC is issued and redeemed in accordance with Circle's blocklisting policy. Circle reserves the right to block the transfer of USDC to and from an address on chain as permitted under the blocklisting policy." — [USDC terms](https://www.circle.com/legal/usdc-terms)
- Circle Stablecoin Access Denial Policy, as extracted from Circle's published PDF: Circle "has the ability to block individual addresses from sending and receiving Circle Stablecoin on every blockchain to which Circle Stablecoin is issued." A denied address "can no longer send or receive Circle Stablecoin and all of the Circle Stablecoin controlled by that address is blocked and cannot be transferred on-chain." "It is not possible to deny access to individual Circle Stablecoin tokens." The policy says Circle will not deny access except for listed exceptions: a threat to the security, integrity, or reliability of the stablecoin network (the example given is compromise of privileged keys such as a minter key); a law, regulation, or legal order from a recognized U.S. or French authority or other government authority with jurisdiction; and certain urgent law-enforcement, sanctions, or national-security requests as described in the policy. "Circle may revert the access denial" when that authority confirms the order is lifted or a security incident no longer requires it. — [Circle Stablecoin Access Denial Policy (PDF)](https://6778953.fs1.hubspotusercontent-na1.net/hubfs/6778953/Circle%20Stablecoin%20Access%20Denial%20Policy_pdf.pdf)
- Circle's irreversibility clause is quoted in the previous section: Circle "does not have the ability to reverse or recall any transaction once initiated" when USDC is sent to a third-party address. — [USDC terms](https://www.circle.com/legal/usdc-terms)
- Solana's token docs: freezing a token account "keeps the same owner, mint, and balance, but prevents the token account from receiving, transferring, or burning tokens until the token account is thawed." A zero-balance frozen account can still be closed. `FreezeAccount` requires the mint's freeze authority as a signer. If that authority is revoked, accounts for that mint can no longer be frozen. Native SOL accounts do not support this freeze. The same page says both the Token Program and the Token Extension Program implement `FreezeAccount`. — [Freeze account](https://solana.com/docs/tokens/basics/freeze-account)
- `spl_token` documents `FreezeAccount` and `ThawAccount` as mint-freeze-authority instructions. Freeze changes an initialized token account to frozen. — [spl_token TokenInstruction](https://docs.rs/spl-token/latest/spl_token/instruction/enum.TokenInstruction.html)
- Secondary descriptions of Circle's Solana mint: Helius says a freeze authority can freeze or thaw individual token accounts "preventing transfers of the token out of their wallet," and points at "the freeze authority for Circle's USDC token on Solana" as something visible on its explorer. Stablescan says Solana USDC uses an SPL freeze authority rather than an in-contract blacklist, that Circle holds that authority, that the balance stays in place, and that this scanner does not index SPL freeze instructions yet. Stablescan also says a frozen USDC account "can still receive USDC, because the freeze blocks transfers out." That receive claim conflicts with Solana's token doc, which says a frozen account cannot receive, transfer, or burn. — [Helius: mint, freeze, and update authority](https://www.helius.dev/docs/orb/explore-authorities); [Stablescan Solana freezes](https://stablescan.achivx.com/solana/freezes)
- USDC terms, "No deposit insurance": "USDC held in your Circle Mint account is not subject to deposit insurance protection," including FDIC and SIPC in the United States and the UK FSCS or an equivalent scheme elsewhere. Separately, the terms say each USDC is intended to be redeemable for 1 USD from Circle through a Circle Mint account, subject to eligibility, terms, law, and fees, and that holders are not entitled to interest on the reserves. Circle "does not guarantee that the value of one (1) USDC will always equal 1 USD on other platforms." — [USDC terms](https://www.circle.com/legal/usdc-terms)

### Inferences
- Circle freeze or access denial is an issuer control used for law, sanctions, security incidents, and terms violations. It is not a sender's undo for a normal family transfer, and it is not something an AI gateway can invoke because a user changed their mind.
- On Solana's token program, freeze leaves the owner and the balance where they are and blocks movement until thaw. It does not transfer the USDC back to the original sender. That is a different act from reversing a finalized transfer.
- Where Solana's docs and Stablescan disagree about receiving into a frozen account, the Solana token documentation is the primary description of `FreezeAccount`. Stablescan is a third-party scanner page and it says it has not indexed Solana freeze transactions.
- The access-denial policy blocks the address's stablecoin generally. It says individual tokens cannot be singled out. A completed payment that already landed in an unblocked recipient account is not pulled back by blocking the sender later. Blocking the recipient would freeze what that recipient now holds, which is still not an "unsend" by the sender.
- Circle's "no deposit insurance" sentence is about USDC in a Circle Mint account. It does not say that self-custodied USDC is a bank deposit. These notes do not describe USDC as an insured deposit.

### Gaps
- This research did not read the on-chain Solana USDC mint account, so it does not independently report the current `freeze_authority` address. Helius and Stablescan attribute that authority to Circle. Circle's own terms describe a right to block on-chain transfers and point at a blocklisting policy; the fetched terms page does not name the Solana freeze-authority pubkey.
- The access-denial policy text above comes from the search extract of Circle's HubSpot PDF, not from a full local parse of the PDF. Wording that matters (every supported chain, whole-address block, no per-token denial, reversal only when the legal basis is lifted) is taken from that extract.
- No fetched Circle page says Circle will freeze a routine mistaken or AI-initiated family transfer on the sender's request.
- Circle's terms say a third-party transfer is irreversible "once initiated" and do not define that phrase against Solana commitment levels.
